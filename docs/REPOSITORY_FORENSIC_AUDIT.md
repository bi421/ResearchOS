### Critical Findings

#### 1. EVIDENCE CONCEPT FRACTURED 4 WAYS — CRITICAL

| Module | Class | Schema | Status |
|--------|-------|--------|--------|
| `objects/evidence.py` | `Evidence` | BaseObject: direction, interpretation, confidence, observation_id | **Canonical domain object** |
| `reasoning_engine/contracts.py` | `EvidenceItem` | Frozen: id, source, evidence_type, content_hash, reliability_score | Isolated — only used by reasoning_engine tests |
| `decision_engine/contracts.py` | `EvidenceItem` | Mutable: source, source_id, direction, strength, weight, confidence | Used by decision_engine + tests |
| `evidence/envelope.py` | `EvidenceEnvelope` | Immutable: artifact_type, artifact_hash, version, payload, lineage_hash | Evidence certification layer |

Four incompatible "evidence" types. No import sharing. The `reasoning_engine.EvidenceItem` and `decision_engine.EvidenceItem` share a name but have completely different schemas.

**Risk:** Future integration will require disambiguation. Currently not a runtime issue because modules are siloed.

#### 2. REPOSITORY PROLIFERATION — 7 IMPLEMENTATIONS — CRITICAL

| Module | Class | Canonical Interface? |
|--------|-------|---------------------|
| `repository/memory.py` | `MemoryRepository` | YES (RepositoryInterface) |
| `storage/repository.py` | `ResearchRepository` | YES (RepositoryInterface) — main production store |
| `data_engine/repository.py` | `DatasetRepository` | NO (different interface) |
| `pipeline_repository/` | `PipelineRepository` | NO (JSON-backed) |
| `intelligence/repository.py` | `EvidenceRepository` | NO (graph-based) |
| `evidence/repository.py` | `EvidenceRepository` | NO (wraps storage/) |
| `market_memory/repository.py` | `MarketMemoryRepository` | NO (wraps MemoryRepository) |

Only 2 of 7 share the canonical `RepositoryInterface`. Each module builds its own storage silo.

**Assessment:** This is architectural fragmentation but not currently causing bugs. Each repository serves a distinct domain. Consolidation would improve maintainability but is high-risk.

#### 3. `agent/` vs `agents/` — DEAD CODE — HIGH

`researchos/agent/` is an empty stub with only `__init__.py` containing a deprecation note. `researchos/agents/` contains the working code (`tools.py`). Only `run_demo.py` imports from `agents/`.

**Verdict: DELETE `researchos/agent/`**

#### 4. `memory/` vs `market_memory/` — PARALLEL IMPLEMENTATIONS — HIGH

| Aspect | `memory/` | `market_memory/` |
|--------|-----------|------------------|
| Purpose | Operational CRUD (record/query events) | Analytical (similarity, matching, outcomes) |
| Entity source | `objects/market_memory.py` | Own `models.py` |
| Storage | RepositoryInterface (injected) | MemoryRepository (in-memory) |
| Importers | 1 test file | 8+ internal + 2 test files |
| Has engine | MarketMemoryEngine | MarketMemoryIntegrator |

Two parallel implementations of "remembering market states" with incompatible object hierarchies. Zero cross-imports.

**Assessment:** `market_memory/` is the active, feature-rich implementation. `memory/engine.py` is a legacy wrapper around `objects/market_memory` types.

#### 5. `pipeline/` vs `orchestration/` — TWO COORDINATORS, CLEAN — MEDIUM

`pipeline/` = research reasoning pipeline (object lifecycle: Observation → Evidence → Hypothesis → Research).
`orchestration/` = ML training pipeline (DatasetBuilder → WalkForwardValidator → Trainer).

Different domains, no overlap. The naming collision is unfortunate but architecturally sound.

#### 6. `engines/` re-exports from `macro/` — MEDIUM

`engines/__init__.py` re-exports `MacroAnalysisEngine` from `macro/engine.py`. This is an encapsulation violation — `engines/` reaches into a peer module.

### Key Findings

1. **Zero import connectivity** — The two modules are completely independent. No file in `researchos/` imports from `macro_intelligence/`, and vice versa.

2. **`researchos/macro/engine.py`** — Single monolithic 1,386-line file. Legacy production engine for XAUUSD heuristic macro scoring. No `__init__.py`. No statistical rigor. Hardcoded thresholds.

3. **`macro_intelligence/`** — 90+ files across 13 subpackages. Proper domain library with frozen dataclasses, deterministic hashing, tier-based import discipline. Zero production integration.

4. **Name collision: `MacroRegime`** — Three completely different classes share this name:
   - `researchos.objects.macro.MacroRegime` (mutable BaseObject)
   - `macro_intelligence.regime.contracts.MacroRegime` (frozen dataclass)
   - `macro_intelligence.regime.classification.taxonomy.MacroRegime` (Enum)

5. **`macro_intelligence/` is NOT in pyproject.toml packages** — It is not installed as part of the `researchos` package.

### Macro Consolidation Recommendation

**DEFER to a dedicated branch** (`macro-consolidation`). This is a significant architectural migration that must not be mixed with general cleanup. The consolidation requires:

- Mapping between incompatible `MacroRegime` types
- Reconciling different inflation/growth/risk taxonomies
- Bridging mutable BaseObject vs frozen dataclass paradigms
- Creating an integration adapter layer

`researchos/macro/engine.py` must remain active (it is wired into the production runtime via `engines/__init__.py`) until a proper bridge is built.

## PHASE 9 — QUANT ENGINE AUDIT

### Architecture: SOUND

The quant engine uses a **certified backend router** pattern:

```
Request → Capability Check → Scheduler → Backend Execution → Validation (vs Python reference) → Success/Fallback
```

- **Python reference backend** is the scientific source of truth
- C++ backend is optional (falls back gracefully with warning)
- Every execution produces immutable `BackendExecutionMetadata` with result hash
- Numerical validation against Python reference is built into the router

### C++ Bridge: WELL-DESIGNED

- `CppQuantAdapter` implements `QuantComputationInterface` exactly
- Schema normalization applied to C++ outputs (count→int, max_drawdown→rounded)
- Falls back to PythonQuantBackend when compiled module unavailable
- C++ engine is C++20, statically linked, MSVC on Windows

### Concerns

- `cpp_quant_engine/python/` has 0% test coverage (pybind11 bridge layer)
- `macro_intelligence/exceptions.py` has 0% coverage (dead code or untested)
- `macro_intelligence/interfaces/` has 0% coverage (untested bridge code)
